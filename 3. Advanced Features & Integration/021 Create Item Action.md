# 021 Create Item Action

Canonical documentation for 021 Create Item Action. This document defines concepts, terminology, and standard usage.

## Purpose
The **021 Create Item Action** serves as the fundamental mechanism for instantiating a new entity within a system of record. Its primary purpose is to transition an object from a state of non-existence to a state of persistence, ensuring that all defined constraints, schemas, and business rules are satisfied before the entity is committed to the system's state.

This action addresses the problem of data entry consistency, identity generation, and the enforcement of initial state invariants in distributed or centralized architectures.

## Core Concepts
### 1. Atomicity
The 021 Create Item Action must be atomic. The Item is either created in its entirety, meeting all requirements, or it is not created at all. There is no valid "partial" state for a Create action.

### 2. Schema Enforcement
Every Item must conform to a predefined schema. This includes data types, required fields, and relationship constraints. The Create action acts as the primary gatekeeper for these constraints.

### 3. Identity Assignment
A critical component of the Create action is the establishment of uniqueness. The system must ensure that the new Item does not violate uniqueness constraints and that its Identity is immutable once persisted.

## Standard Model
The standard model for the 021 Create Item Action follows a linear progression:

1.  **Ingestion:** The system receives the Payload.
2.  **Syntactic Validation:** The system checks for malformed data, incorrect types, or missing mandatory fields.
3.  **Semantic/Business Validation:** The system checks for logical consistency (e.g., "Does the referenced Parent ID exist?").
4.  **Identity Generation:** If an ID is not provided (or if system-generated IDs are mandated), the system generates a unique identifier.
5.  **Transformation:** The system may append metadata (e.g., `created_at` timestamps, `creator_id`).
6.  **Persistence:** The Item is written to the storage layer.
7.  **Acknowledgment:** The system returns a success confirmation along with the final state of the Item (including the ID).

## Common Patterns
*   **Synchronous Creation:** The requester waits for the persistence step to complete before receiving a response. Used when immediate confirmation is required.
*   **Asynchronous (Queued) Creation:** The system acknowledges receipt of the request, but the actual creation occurs later. Used for high-volume or resource-intensive operations.
*   **Client-Generated ID:** The requester provides a UUID/ULID, allowing for easier idempotency handling and offline creation.
*   **Factory Pattern:** A specialized service or module is responsible for the instantiation logic to ensure complex business rules are applied consistently.

## Anti-Patterns
*   **The "Upsert" Ambiguity:** Using the Create action to also update existing items without explicit intent. This leads to accidental data overwrites.
*   **Validation Bypass:** Allowing items to be persisted via "backdoor" channels that do not trigger the 021 validation logic.
*   **Leaking Internal State:** Returning sensitive system metadata (e.g., physical database addresses or internal stack traces) in the acknowledgment response.
*   **Non-Deterministic ID Generation:** Using ID generation methods that can produce collisions under high concurrency.

## Edge Cases
*   **Race Conditions:** Two simultaneous requests attempting to create an item with the same unique attribute. The system must implement locking or unique constraints to fail one request gracefully.
*   **Partial Success in Distributed Systems:** If an item must be created across multiple microservices, a failure in one must trigger a rollback (Saga pattern) to maintain the "In-Scope" atomicity.
*   **Payload/Schema Mismatch:** Handling "extra" fields in a payload. Systems must decide whether to ignore unknown fields (Strict) or reject the request (Lax).
*   **Timeouts during Persistence:** If the requester times out before receiving an acknowledgment, the system must provide a way to query if the creation was successful (Idempotency Keys).
