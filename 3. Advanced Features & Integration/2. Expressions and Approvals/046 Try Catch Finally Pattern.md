# 046 Try Catch Finally Pattern

Canonical documentation for 046 Try Catch Finally Pattern. This document defines concepts, terminology, and standard usage.

## Purpose
The Try Catch Finally pattern exists to provide a structured mechanism for handling exceptional conditions and ensuring state integrity during program execution. It addresses the problem of non-linear control flow caused by runtime errors, hardware interruptions, or unexpected data states. By decoupling the "happy path" logic from error-handling logic, the pattern allows systems to fail gracefully, maintain resource safety, and provide diagnostic information without immediate process termination.

> This documentation is intended to be implementation-agnostic and authoritative.

## Core Concepts

### 1. Guarded Execution
The pattern operates on the principle of "guarded execution." The system attempts to execute a sequence of operations within a boundary. If any operation within that boundary violates the expected execution model, the system immediately diverts control to a predefined recovery path.

### 2. Exception Propagation
When an exception occurs, the system searches for the nearest matching handler. If the current scope does not contain a handler, the exception "bubbles up" through the call stack. This allows high-level logic to decide how to handle errors generated by low-level utilities.

### 3. The Finally Guarantee
The `Finally` block represents a deterministic finalization phase. Its primary purpose is to release resources (file handles, network sockets, database connections) that were acquired in the `Try` block, ensuring that the system does not leak resources even in the event of a catastrophic failure.

## Standard Model

The standard model follows a specific execution sequence:

1.  **Try Phase:** The system enters the `Try` block.
2.  **Interruption Check:**
    *   If **no exception** occurs: The `Try` block completes; the `Catch` block is skipped.
    *   If an **exception** occurs: Execution of the `Try` block halts; the system searches for a matching `Catch` block.
3.  **Catch Phase (Optional):** If a match is found, the `Catch` block executes. If the `Catch` block rethrows the exception or throws a new one, the exception continues to propagate *after* the `Finally` block executes.
4.  **Finally Phase:** The `Finally` block executes regardless of the outcomes in the previous phases.
5.  **Resumption:** If the exception was handled and not rethrown, execution continues after the `Finally` block.

## Common Patterns

### Resource Cleanup
The most common use case is ensuring that external resources are closed.
*   *Pattern:* Open resource in `Try`, use resource in `Try`, close resource in `Finally`.

### Log and Rethrow
Used when a local scope needs to record that an error occurred for diagnostic purposes but cannot resolve the error itself.
*   *Pattern:* Catch exception, log the stack trace/metadata, and re-raise the same exception to the caller.

### Translation/Wrapping
Converting a low-level implementation-specific error into a high-level domain-specific error.
*   *Pattern:* Catch a `SqlException` and throw a `UserDataAccessError`.

### Graceful Degradation
Providing a fallback value or behavior when a primary operation fails.
*   *Pattern:* Try to fetch data from a cache; if it fails, catch the error and fetch from a slower database.

## Anti-Patterns

### 1. The "Pokémon" Catch (Catch-All)
Catching the most base-level exception type (e.g., `catch (Exception e)`) without specific handling logic. This hides bugs (like Null Pointer references) that should otherwise cause a crash or be handled specifically.

### 2. Swallowing Exceptions
Catching an exception and leaving the block empty. This makes debugging nearly impossible as the system state becomes corrupted without any record of the failure.

### 3. Logic in Finally
Placing complex business logic or code that can itself throw exceptions inside a `Finally` block. If a `Finally` block throws an exception, it often masks the original exception that triggered the block, leading to "Lost Exceptions."

### 4. Using Exceptions for Flow Control
Using Try/Catch to handle expected logic (e.g., checking if a file exists by trying to open it and catching the error). Exceptions should be reserved for *exceptional* (unexpected) events, as they are computationally expensive and reduce code readability.

## Edge Cases

### 1. Return Statements in Finally
In many implementations, if a `return` statement is placed inside a `Finally` block, it will override any `return` statement in the `Try` or `Catch` blocks. This can lead to unexpected return values.

### 2. Process Termination
If the execution environment encounters a fatal error (e.g., Out of Memory, Stack Overflow, or a forced process kill), the `Finally` block may never execute. The "guarantee" of `Finally` is limited to the constraints of the runtime environment.

### 3. Nested Exceptions
If an exception is thrown inside a `Catch` block while another exception is being handled, the original exception is typically lost unless the language supports "Suppressed Exceptions" or "Inner Exceptions."

### 4. Thread Interruption
In multi-threaded environments, interrupting a thread may or may not trigger `Finally` blocks depending on the specific implementation of the threading model and how it handles signals.
